# Audit SEO — onmec-site

**Date** : 30 août 2026
**Périmètre** : le code de `onmec-site` (site public, avant mise en ligne) + état du site actuellement
servi sur `mec-ci.org` en tant que contrainte de migration.
**Méthode** : lecture du code, plus vérification empirique contre le serveur de dev (`localhost:3000`)
et contre le site de production `mec-ci.org`. Chaque constat cité ci-dessous a été soit vérifié en
direct (marqué **vérifié**), soit tracé à un `fichier:ligne`.

---

## 0. Contexte : deux sites distincts

Il faut séparer deux choses qui portent le même nom.

1. **`onmec-site`** (ce dépôt) : le nouveau site, vinext / Cloudflare Workers. Il est déployé sur
   **`https://onmec-site.kouakoucaxel.workers.dev`** (vérifié : HTTP 200), et **pas** sur
   `mec-ci.org` — `wrangler.jsonc` ne contient aucun bloc `routes`. **C'est le sujet de cet audit.**

   Conséquence directe sur la configuration : `SITE_URL` doit désigner workers.dev tant que la
   bascule n'a pas eu lieu. Pointer les canonicals vers `mec-ci.org` aujourd'hui les ferait
   référencer le contenu de l'ancien site — un canonical vers une page sans rapport est pire que
   pas de canonical du tout.

2. **Le site actuellement en ligne sur `mec-ci.org`** : une SPA Vite hébergée chez Hostinger
   (`X-Powered-By: Hostinger Horizons`, `<meta name="generator" content="Mec-ci">`). Aucun code
   partagé avec ce dépôt. Son état SEO est traité en §4 (Migration), parce qu'il détermine ce qu'il
   faut prévoir au moment de la bascule — pas parce qu'il est corrigeable ici.

**La bonne nouvelle** : le nouveau site n'a pas encore d'historique d'indexation à protéger. Tout ce
qui suit est à faire *avant* la mise en ligne, pas à réparer après.

## 1. Synthèse

### Ce qui est déjà correct

Il faut le dire, parce que ce sont précisément les pièges où le site legacy est tombé :

| Point | État | Preuve |
|---|---|---|
| Rendu serveur du contenu | ✅ Les 9 pages publiques sont des Server Components ; le texte est dans le HTML initial | `app/(public)/**`, un seul `"use client"` : `error.tsx:1` |
| Code HTTP 404 | ✅ Une URL inexistante renvoie un vrai **404** | **vérifié** : `/cette-page-nexiste-pas-12345` → HTTP 404 |
| `<meta viewport>` | ✅ Injecté par vinext, malgré le `<head>` écrit à la main | **vérifié** dans le HTML rendu |
| `lang="fr"` | ✅ | `app/layout.tsx:24` |
| Un seul `<h1>` par page | ✅ sur les 7 pages statiques | **vérifié** : `h1x1` partout |
| Liens internes crawlables | ✅ `next/link` partout, aucun `router.push` en guise de navigation | `site-header.tsx`, `article-card.tsx:10`, etc. |
| Pagination de `/actualites` | ✅ En URL (`?categorie=…&page=N`), rendue serveur | `news-list.tsx:22-28,132-145` |
| Site mono-langue | ✅ Pas de hreflang à gérer, pas de piège i18n | — |

### Les 5 problèmes prioritaires

1. **Aucune métadonnée par page.** Un seul `export const metadata` dans tout le dépôt
   (`app/layout.tsx:7`). Les 9 pages publiques partagent le même `<title>` et la même `description`.
2. **Ni `sitemap.ts` ni `robots.ts`.** Rien ne déclare aux moteurs ce qui existe.
3. **Aucun canonical, aucun `metadataBase`.** Rien ne tranche entre `www` et non-`www`, ni entre
   variantes de paramètres.
4. **91 documents sur 100 sont hors d'atteinte des crawlers** sur `/ressources` : la pagination est
   en state client, sans URL.
5. **`/actions` est orpheline** : aucun lien entrant dans tout le dépôt, et pas de sitemap pour
   compenser. La page est en ligne et invisible.

### Gains rapides

- `app/robots.ts` et `app/sitemap.ts` : deux fichiers, ~40 lignes, débloquent les points 2 et 5.
- `noindex` sur `/admin/*` et `/maintenance`.
- Trois `alt=""` à remplacer par `article.title` (la donnée est déjà là).

> **Avertissement sur les recommandations.** Les correctifs ci-dessous ont été formulés en tenant
> compte du fait que **vinext est une réimplémentation de l'API Next, pas Next lui-même**. Deux
> points ont été vérifiés plutôt que supposés : `<meta viewport>` est bien injecté
> automatiquement (donc rien à faire), mais `next/font` **n'est pas disponible** (§2.7). Pour toute
> API Next non listée dans `CLAUDE.md`, vérifier avant d'implémenter.

## 2. SEO technique

### 2.1 — Aucune métadonnée par page

- **Impact** : Élevé (P1)
- **Preuve** : Un seul `export const metadata` dans `app/` — `app/layout.tsx:7-18`. Aucun
  `generateMetadata`. **Vérifié en direct** contre le serveur de dev :

  ```
  /            [200] T: MEC — Mouvement pour l'Éducation à la Citoyenneté
  /actions     [200] T: MEC — Mouvement pour l'Éducation à la Citoyenneté
  /actualites  [200] T: MEC — Mouvement pour l'Éducation à la Citoyenneté
  /apropos     [200] T: MEC — Mouvement pour l'Éducation à la Citoyenneté
  /contact     [200] T: MEC — Mouvement pour l'Éducation à la Citoyenneté
  /rejoindre   [200] T: MEC — Mouvement pour l'Éducation à la Citoyenneté
  /ressources  [200] T: MEC — Mouvement pour l'Éducation à la Citoyenneté
  ```

  Les descriptions sont identiques elles aussi. Le cas le plus coûteux est celui des pages
  dynamiques : un article dont le titre est déjà chargé côté serveur
  (`actualites/article-header.tsx:33` affiche `article.title` dans le `<h1>`) sort malgré tout avec
  le titre générique. **Vérifié** sur
  `/actualites/cap-sur-laction-des-initiatives-citoyennes-…` → `<title>MEC — Mouvement pour…`.

- **Conséquence** : Google réécrit les titres quand ils sont dupliqués, mais il le fait mal et de
  façon instable. Surtout, le `<title>` est le premier signal de pertinence d'une page : sept pages
  qui déclarent toutes le même sujet ne peuvent se positionner sur aucun sujet en particulier.

- **Correctif** :
  1. Ajouter `metadataBase: new URL(getSiteUrl())` et un `title.template` dans `app/layout.tsx` :
     ```ts
     title: {
       default: "MEC — Mouvement pour l'Éducation à la Citoyenneté",
       template: "%s | MEC",
     },
     ```
  2. Un `export const metadata` par page statique (7 pages), avec `alternates: { canonical: "/…" }`.
  3. Un `generateMetadata` sur `/actualites/[slug]` et `/ressources/[id]`, alimenté par la donnée
     déjà chargée. Point de vigilance : réutiliser la même fonction de `features/*/requests/` que la
     page, puis **vérifier dans les logs que l'appel API n'est pas doublé** sur un rendu. Next
     mémoïse les `fetch` identiques au sein d'un même rendu, mais vinext est une réimplémentation —
     cette parité n'est pas acquise et n'a pas été testée ici. Si l'appel est doublé, mémoïser
     explicitement.

  Une `description` de 150-160 caractères par page, distincte, dérivée du chapô pour les articles.

### 2.2 — Ni `robots.ts` ni `sitemap.ts`

- **Impact** : Élevé (P1)
- **Preuve** : Aucun `robots.ts` / `sitemap.ts` dans `app/`, aucun `.xml` dans `public/`
  (`public/` ne contient que `apple-icon.png`, `assets/`, `favicon.ico`, `icon.png`).
- **Conséquence** : la découverte repose entièrement sur le maillage interne. Or le maillage a deux
  trous documentés plus bas (§2.4 et §3.4) : `/actions` n'a aucun lien entrant, et 91 documents de
  `/ressources` non plus. Sans sitemap, ces URLs n'existent pas pour un moteur.
- **Correctif** : `app/robots.ts` (autoriser tout sauf `/admin` et `/api`, déclarer le sitemap) et
  `app/sitemap.ts` (les 7 routes statiques + les articles + les documents, tirés des mêmes fonctions
  `features/*/requests/`). C'est le correctif au meilleur rapport effort/impact du lot.

### 2.3 — Aucun canonical ni arbitrage `www` / non-`www`

- **Impact** : Élevé (P1)
- **Preuve** : zéro occurrence de `canonical`, `metadataBase`, `openGraph` ou `robots` dans tout le
  code TS/TSX (recherche ripgrep sur `*.{ts,tsx}` : aucun résultat). Et sur le domaine actuel,
  **vérifié** : `https://mec-ci.org/` et `https://www.mec-ci.org/` répondent toutes deux HTTP 200
  avec un contenu identique (même empreinte MD5), sans redirection.
- **Conséquence** : si la bascule reproduit cette configuration, chaque page existera en double.
- **Correctif** : choisir une forme canonique, rediriger l'autre en 301 au niveau Cloudflare, et
  poser `alternates.canonical` sur chaque page. `/actualites?page=2` doit se canonicaliser vers
  lui-même, jamais vers `/actualites` — sinon les pages 2+ disparaissent de l'index.

### 2.4 — `/actions` est orpheline

- **Impact** : Élevé (P1)
- **Preuve** : le lien est commenté dans la nav (`features/site/data/nav-links.ts:4`) et dans les
  raccourcis de contact (`contact/contact-cta.tsx:4`). Aucun lien entrant ailleurs dans le dépôt.
- **Conséquence** : c'est la page la plus fournie du site en contenu propre (3 programmes +
  chronologie) et elle est inatteignable, au crawl comme pour un visiteur.
- **Correctif** : soit la remettre dans la navigation, soit — si elle n'est pas prête — la retirer
  du build. Une page publiée sans chemin d'accès est le pire des deux mondes. À trancher côté
  produit, mais à trancher avant la mise en ligne.

### 2.5 — `/admin/connexion` est indexable

- **Impact** : Moyen (P2)
- **Preuve** : **vérifié** — `/admin/connexion` répond HTTP 200, sans `<meta name="robots">`, avec le
  même `<title>` générique que le site public. `/admin` lui-même redirige bien en 307 vers la page
  de connexion (`proxy.ts:44-56`), donc seule la page de login est exposée.
- **Conséquence** : une page de connexion indexée n'apporte rien et dilue le signal. Le commentaire
  dans `admin-auth/auth-screen.tsx:40` affirme d'ailleurs « non référencé depuis le site public » —
  c'est vrai du maillage, mais rien ne l'empêche techniquement d'être indexée.
- **Correctif** : `robots: { index: false, follow: false }` dans un `metadata` sur
  `app/admin/layout.tsx`, plus l'exclusion de `/admin` dans `robots.ts`.

### 2.6 — `/maintenance` est atteignable et indexable

- **Impact** : Moyen (P2)
- **Preuve** : **vérifié** — `/maintenance` répond HTTP 200. Aucun lien interne ne pointe vers elle
  dans tout le dépôt (seul l'import du composant `MaintenanceRetryButton` apparaît). C'est donc,
  comme `/actions`, une page orpheline — mais celle-ci ne doit *jamais* être indexée.
- **Conséquence** : une page « site en maintenance » dans les résultats de recherche est un signal
  très négatif, et elle serait présentée avec le même titre générique que le reste du site.
- **Correctif** : `robots: { index: false }` sur la page, et exclusion explicite dans `robots.ts` et
  du `sitemap.ts`. À traiter en même temps que le `noindex` de l'espace admin (§2.5).

### 2.7 — Google Fonts en `<link>` bloquant

- **Impact** : Moyen (P2) — Core Web Vitals / LCP
- **Preuve** : `app/layout.tsx:28-31` charge la feuille de style depuis `fonts.googleapis.com` via un
  `<link rel="stylesheet">` écrit à la main. Les `preconnect` (`:26-27`) atténuent, mais ne
  suppriment pas, l'aller-retour cross-origin bloquant le rendu.
- **Conséquence** : retard direct sur le LCP, sur un site dont l'audience est majoritairement
  ivoirienne — donc souvent en réseau mobile contraint, là où un aller-retour supplémentaire coûte
  cher.
- **Correctif** : **attention, `next/font/google` n'est pas disponible ici.** Vérifié :
  `require.resolve("next/font/google")` échoue en `MODULE_NOT_FOUND`, il n'y a aucun paquet `next`
  installé, et `vinext@1.0.0-beta.8` ne déclare aucun export `font`. La parité `next/*` annoncée
  dans `CLAUDE.md` couvre les modules de runtime (`next/headers`, `next/server`), pas ce chargeur
  qui exige une étape de build.

  Le correctif est donc manuel : télécharger les fichiers `woff2` d'Instrument Sans et Instrument
  Serif, les placer dans `public/fonts/`, et déclarer les `@font-face` dans `globals.css` avec
  `font-display: swap` et un `<link rel="preload" as="font" crossorigin>` pour les deux graisses
  réellement utilisées au-dessus de la ligne de flottaison. Cela supprime la feuille de style
  tierce bloquante et les deux `preconnect`.

### 2.8 — URLs des ressources en UUID

- **Impact** : Moyen (P2)
- **Preuve** : **vérifié** — `/ressources/11002588-3dc7-453c-9734-8791907f2214`. Incohérent avec
  `/actualites/[slug]`, qui utilise bien des slugs lisibles.
- **Conséquence** : l'URL ne porte aucun mot-clé et n'est ni mémorisable ni partageable à l'oral.
- **Correctif** : passer à un slug (`/ressources/guide-du-jeune-citoyen`) si le backend expose ou
  peut exposer un champ slug. À arbitrer avec l'équipe backend — le changement est plus simple
  maintenant qu'après indexation. Si ce n'est pas possible à court terme, ce n'est pas bloquant :
  c'est le seul point de cette section qui peut attendre la V2.

## 3. SEO on-page

### 3.1 — Aucun Open Graph ni Twitter Card

- **Impact** : Moyen (P2)
- **Preuve** : zéro occurrence de `openGraph` ou `twitter` dans le code.
- **Conséquence** : pas d'effet direct sur le classement, mais un effet direct sur le partage. Pour
  une association dont la diffusion passe largement par WhatsApp et Facebook, un lien partagé sans
  image ni titre spécifique perd une grande partie de ses clics. C'est le canal principal, pas un
  détail.
- **Correctif** : `openGraph` dans le `metadata` racine (type `website`, `locale: "fr_CI"`, image par
  défaut) et surchargé par article dans `generateMetadata` avec l'image de couverture réelle.

### 3.2 — Aucune donnée structurée (JSON-LD)

- **Impact** : Moyen (P2)
- **Preuve** : zéro occurrence de `ld+json`, `JsonLd` ou `schema.org` dans le dépôt. Ce constat est
  **autoritaire** ici : contrairement à un site sous CMS où un plugin peut injecter du JSON-LD côté
  client, tout le code de rendu est dans ce dépôt.
- **Correctif**, par ordre de rendement :
  1. `Organization` (ou `NGO`) sur la page d'accueil : nom, logo, `sameAs` vers les réseaux,
     `contactPoint`. C'est ce qui alimente le panneau de connaissance.
  2. `NewsArticle` sur `/actualites/[slug]` : `headline`, `datePublished`, `image`, `author`.
  3. `BreadcrumbList` sur les pages profondes.

### 3.3 — `alt=""` sur de vraies images de contenu

- **Impact** : Moyen (P2) — accessibilité autant que SEO
- **Preuve** : trois couvertures d'article réelles portent un `alt` vide, alors que `article.title`
  est disponible localement :
  - `components/features/site/article-card.tsx:14` — se propage à `/`, `/actualites` et au bloc
    « À lire aussi »
  - `components/features/actualites/news-list.tsx:80` — l'article à la une
  - `components/features/actualites/article-header.tsx:58` — l'image d'en-tête, qui porte `priority`
- **Correctif** : `alt={article.title}` aux trois endroits. Correction d'une ligne chacune.
- **À noter** : `accueil/hero.tsx:40-44` a bien `alt=""` **à raison** — c'est un filigrane décoratif.
  Les fiches documents (`librairie-card.tsx:13`, `document-header.tsx:31`, …) passent correctement
  `alt={document.title}`.
- **Angle mort** : `sanitize-article-html.ts:29,38` autorise `<img>` sans imposer `alt`. Une image
  insérée dans Tiptap sans texte alternatif passera telle quelle. À traiter côté éditeur ou en
  imposant l'attribut au nettoyage.

### 3.4 — `/ressources` : seuls 9 documents atteignent le HTML

- **Impact** : Élevé (P1)
- **Preuve** :
  - `features/librairie/requests/list-librairie-public.ts:7` — `CATALOG_LIMIT = 100` : le serveur
    récupère le catalogue jusqu'à 100 documents.
  - `librairie-catalog.tsx:16` — `PAGE_SIZE = 9`, et `:46` `filtered.slice(...)`.
  - **Vérifié en direct** : la page rendue ne contient que **9** liens `/ressources/{id}` uniques.
  - `librairie-catalog.tsx:25-28` — `query`, `categorie`, `sort` et `page` sont tous en `useState`,
    sans reflet dans l'URL.
  - `librairie-pagination.tsx:14-42` — uniquement des `<button onClick>`, aucun `<a>`.
- **Conséquence** : au-delà des 9 premières, les fiches n'ont aucune URL de découverte — ni
  pagination, ni page de catégorie, ni sitemap. Le nombre exact de documents concernés dépend du
  volume réel en production (plafond de récupération : 100) ; en local, 9 sur l'ensemble du
  catalogue sont atteignables. Une bibliothèque de documents pédagogiques est pourtant exactement le
  type de contenu qui capte de la recherche longue traîne — c'est probablement le gisement de trafic
  organique le plus important du site, et il est fermé.
- **Correctif** : aligner sur ce que `/actualites` fait déjà bien (`news-list.tsx:132-145`) — passer
  les filtres et la pagination en `searchParams` avec des `<Link>`, en rendu serveur. Le sitemap
  (§2.2) couvre les fiches individuelles, mais ne remplace pas un maillage réel.

### 3.5 — Hiérarchie de titres : sauts de niveau

- **Impact** : Faible à moyen (P3)
- **Preuve** :
  - `/apropos` — deux sauts `h1 → h3` : `cibles-section.tsx:22` et `vision.tsx:19` (les intitulés de
    section au-dessus sont des `<span>`, `:8-10`). `mission.tsx` n'a aucun titre.
  - `/ressources` — `h1 → h3` : le catalogue ne pose aucun `h2`, les cartes sont des `h3`
    (`librairie-card.tsx:20`). Le premier `h2` est tout en bas (`librairie-cta.tsx:19`).
  - `/actualites?page=2` — le `h2` « à la une » est conditionné à la page 1
    (`news-list.tsx:43,98`), donc les pages 2+ passent de `h1` directement aux `h3` des cartes.
  - `/rejoindre` — **aucun `h2`** sur toute la page : les 4 intitulés du formulaire sont des `<span>`
    dans des `<legend>` (`join-form.tsx:47-52,68-73,106-111,154-159`).
- **Correctif** : promouvoir en `h2` les intitulés de section qui sont aujourd'hui des `<span>`.
  Purement sémantique, sans impact visuel si les classes sont conservées.
- **Risque de multi-`h1`** : `sanitize-article-html.ts:19` autorise `h1` dans le corps d'article. Un
  rédacteur qui en pose un crée une page à deux `h1`. Retirer `h1` de la liste blanche règle le cas
  à la source.

### 3.6 — Liens morts en pied de page

- **Impact** : Faible (P3) — mais signal de confiance
- **Preuve** : `site-footer.tsx:72` et `:75` — `<a href="#">` pour « Mentions légales » et
  « Confidentialité », sur toutes les pages du site.
- **Conséquence** : les pages de mentions légales et de confidentialité comptent parmi les signaux de
  confiance élémentaires (volet *Trustworthiness* de l'E-E-A-T). Les annoncer puis ne pas les fournir
  est pire que de ne rien annoncer.
- **Correctif** : créer les deux pages, ou retirer les liens en attendant.
- **Voisins** : boutons de partage non fonctionnels — `document-header.tsx:79-88` (des `<span>` sans
  `href` ni handler) et `article-header.tsx:45-50`. Sans effet SEO, mais même nature de dette.

## 4. Contenu et E-E-A-T

### 4.1 — Texte de remplissage indexable

- **Impact** : Élevé (P1) si la mise en ligne a lieu en l'état
- **Preuve** : des mentions « à fournir » / « à confirmer » sont rendues côté serveur, donc
  indexables :
  - `accueil/partners.tsx:4` (« Partenaire 1/2/3 »), `:26` (« Logo à fournir »), `:47`
  - `accueil/impact-stats.tsx:32` — « Périodes de référence à confirmer avant publication »
  - `accueil/hero.tsx:46` — « Photo de terrain à fournir »
  - `apropos/bureau-section.tsx:19` — « Noms et fonctions à confirmer »
  - `contact/contact-details.tsx:12,15,49` — adresse, numéro et plan d'accès « à fournir »
- **Conséquence** : ces chaînes se retrouvent dans l'index et dans les extraits de résultats. Sur la
  page contact d'une organisation, une adresse et un téléphone manquants coûtent en plus toute
  chance de référencement local.
- **Correctif** : bloquant avant mise en ligne. Soit la donnée réelle, soit le retrait du bloc.

### 4.2 — Chiffres d'impact incohérents entre pages

- **Impact** : Moyen (P2)
- **Preuve** : `accueil/impact-stats.tsx:4-9` annonce « 1 000+ », « 10+ », « 7+ », « 2 ans », tandis
  que `actions/hero.tsx:4-8` annonce « 34 campus », « 28 clubs », « 12 400 personnes depuis 2021 ».
  Les deux séries ne se recoupent pas.
- **Conséquence** : contradiction interne visible par un lecteur, et aucune source citée. C'est
  précisément ce que le volet *Trustworthiness* de l'E-E-A-T pénalise.
- **Correctif** : une source unique de vérité pour ces chiffres, avec une période de référence
  affichée.

### 4.3 — Pages minces

- **Impact** : Moyen (P2)
- **Preuve** :
  - `/rejoindre` — hero de deux phrases (`hero.tsx:19-22`) puis un formulaire. Aucun texte
    descriptif.
  - `/contact` — hero, formulaire, 4 cartes.
  - `/` — hors hero et 3 cartes d'article, environ six phrases de contenu propre. La section
    « Nos actions » est masquée (`page.tsx:7-8`).
  - `/ressources/[id]` — sans `description`, `document-body.tsx:4` renvoie `null` : il ne reste que
    le titre, quelques métadonnées et un bouton de téléchargement.
- **Correctif** : pour `/rejoindre`, quelques paragraphes sur ce qu'implique l'engagement répondent à
  une intention de recherche réelle (« comment rejoindre une association citoyenne en Côte
  d'Ivoire »). Pour `/ressources/[id]`, rendre la description obligatoire côté back-office.

### 4.4 — Boilerplate dupliqué sur les fiches documents

- **Impact** : Moyen (P2)
- **Preuve** : `document-body.tsx:14-18` — un paragraphe de licence d'usage identique sur chaque
  fiche. Combiné à 4.3, une fiche sans description se réduit à ce paragraphe partagé.
- **Conséquence** : un ensemble de pages quasi identiques, exactement le profil « contenu dupliqué /
  peu utile ». Le système de contenu utile de Google évalue le site dans son ensemble : une centaine
  de fiches vides peut peser sur le classement des bonnes pages.
- **Correctif** : description obligatoire, et le texte de licence en pied de page plutôt que dans le
  corps.

### 4.5 — Ni date ni auteur exposés sur les articles

- **Impact** : Moyen (P2)
- **Preuve** : **vérifié** — aucun `<time>` ni attribut `datetime` dans le HTML d'un article rendu.
- **Conséquence** : pour de l'actualité, la date est un signal de fraîcheur de premier ordre, et
  l'auteur un signal d'expertise. Leur absence prive aussi le `NewsArticle` de §3.2 de ses champs
  `datePublished` et `author`.
- **Correctif** : afficher la date en `<time datetime="…">` dans l'en-tête d'article, et l'auteur si
  la donnée existe côté API.

## 5. Migration depuis le site actuel

### 5.1 — État du site legacy (`mec-ci.org`)

Constaté en direct, à titre de contexte de bascule :

| Contrôle | Résultat |
|---|---|
| Taille du HTML de l'accueil | 4 181 octets |
| Texte dans le `<body>` | **aucun** — coquille SPA, tout est rendu par JS |
| `<title>` | `Mec-ci` (générique, pour tout le site) |
| `<meta name="description">` | absente |
| `<link rel="canonical">` | absent |
| `<h1>` dans le HTML | absent |
| `/robots.txt` | renvoie la page HTML en **200** — donc inexistant |
| `/sitemap.xml` | renvoie la page HTML en **200** — donc inexistant |
| URL inexistante | **HTTP 200** — soft-404 sur l'intégralité du site |
| `www` vs non-`www` | les deux en 200, contenu identique, aucune redirection |
| HSTS | absent |

Le soft-404 généralisé est le point le plus grave : n'importe quelle URL, y compris fautive ou
inventée, renvoie 200 avec la coquille de l'application. Combiné à l'absence de sitemap et de contenu
serveur, il faut s'attendre à une profondeur d'indexation très faible aujourd'hui.

**Ce que cela implique** : la migration se fait depuis une base d'autorité quasi nulle. C'est une
contrainte faible — peu à préserver — mais aussi une opportunité : le nouveau site part sans dette,
à condition de ne pas reproduire ces erreurs. Il évite déjà les deux principales (contenu rendu
serveur, vrai 404).

### 5.2 — Correspondance des URLs

Routes du site legacy, extraites de son bundle JavaScript
(`/assets/index-0ff572ae.js`, table de routage du routeur client). Inventaire vérifié en deux passes
distinctes sur le bundle — aucune route supplémentaire trouvée à la seconde :

| URL legacy | Nouvelle URL | Action |
|---|---|---|
| `/` | `/` | — |
| `/actualites` | `/actualites` | — |
| `/actualites/:slug` | `/actualites/[slug]` | vérifier que les slugs sont identiques |
| `/contact` | `/contact` | — |
| `/about` | `/apropos` | **301 requise** |
| `/documents` | `/ressources` | **301 requise** |
| — | `/actions`, `/rejoindre`, `/ressources/[id]` | nouvelles pages |

Deux redirections permanentes à prévoir. Le point à vérifier avec le backend est la conservation des
slugs d'articles : si la base est la même, `/actualites/:slug` bascule sans rien faire ; sinon il
faut une table de correspondance.

### 5.3 — Liste de contrôle de bascule

1. Trancher `www` vs non-`www`, et rediriger l'autre en 301.
2. Poser les deux 301 : `/about` → `/apropos`, `/documents` → `/ressources`.
3. Déployer `robots.ts` et `sitemap.ts` **en même temps** que la bascule, pas après.
4. Vérifier les slugs d'articles entre l'ancienne et la nouvelle base.
5. Créer la propriété Search Console sur le domaine et y soumettre le sitemap.
6. Ajouter HSTS au niveau Cloudflare.
7. Après bascule, surveiller le rapport d'indexation pendant deux à trois semaines.

## 7. Non couvert par cet audit

Par honnêteté sur le périmètre :

- **Core Web Vitals réels** : le constat sur les polices (§2.7) est déduit du code, pas mesuré. Le
  site étant déployé sur `onmec-site.kouakoucaxel.workers.dev`, une mesure PageSpeed Insights est
  possible dès maintenant sur cette URL — et la comparaison avant/après auto-hébergement des
  polices y serait directement observable.
- **Positionnement actuel et trafic organique** : sans accès Search Console ni analytics, aucune
  base de référence. À établir avant la bascule pour pouvoir mesurer l'effet.
- **Recherche de mots-clés et concurrence** : hors périmètre d'un audit technique. C'est pourtant ce
  qui devrait guider la rédaction des `title` et `description` du point P1-2 — à faire idéalement
  avant, ou à réviser juste après.
- **Profondeur d'indexation réelle du site legacy** : déduite (soft-404 généralisé, aucun sitemap,
  aucun contenu serveur), non mesurée. Une requête `site:mec-ci.org` la confirmerait en une minute.
